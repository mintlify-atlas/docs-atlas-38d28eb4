Rekono manages wordlists as first-class resources that are attached to tasks and fed directly to enumeration tools at runtime. Rather than hardcoding file paths in tool configurations, you register wordlists once in Rekono and then select them by name when creating a task, giving every member of a project access to a shared library of tested, version-controlled word files.

## What Wordlists Are Used For

Rekono wordlists supply the input files that enumeration and brute-force tools iterate over during a scan. The two supported wordlist types map directly to the categories of tools that consume them.

<CardGroup cols={2}>
  <Card title="Endpoint wordlists" icon="folder-tree">
    Used by directory and path discovery tools such as **Dirsearch** and **Gobuster** to enumerate web application routes, files, and hidden endpoints. Each line in the file is tried as a path segment against the target URL.
  </Card>
  <Card title="Subdomain wordlists" icon="sitemap">
    Used by subdomain brute-force tools to discover hostnames under a target domain. Each line is prepended to the base domain and resolved via DNS to find live subdomains.
  </Card>
</CardGroup>

Rekono passes the resolved file path of the selected wordlist directly to the tool's command-line argument at execution time via the `WORDLIST` input keyword mapping. Only wordlists whose `type` matches the argument's filter are offered as valid inputs for a given tool configuration.

## Pre-Installed Wordlists

The Docker Compose stack mounts two widely-used wordlist collections as named volumes. These are discovered automatically by the `initializer` service on first run and registered as built-in wordlists that every Admin and Auditor can use without any upload step.

<Tabs>
  <Tab title="SecLists">
    **Volume:** `wordlists_seclists`
    **Mount path:** `/usr/share/seclists`

    SecLists is the most comprehensive collection of security-testing word files, covering common passwords, usernames, web content paths, fuzzing payloads, sensitive data patterns, and more. Rekono mounts it in the `initializer` and `tasks-worker` containers and registers the files it finds there as system wordlists.

    ```yaml
    volumes:
      - wordlists_seclists:/usr/share/seclists
    ```
  </Tab>
  <Tab title="Dirb wordlists">
    **Volume:** `wordlists_dirb`
    **Mount path:** `/usr/share/dirb/wordlists`

    The classic Dirb wordlist set ships with many Linux penetration-testing distributions and provides curated lists of common web content paths organized by target type (Apache, IIS, generic CGI, etc.).

    ```yaml
    volumes:
      - wordlists_dirb:/usr/share/dirb/wordlists
    ```
  </Tab>
</Tabs>

<Note>
  `wordlists_seclists` and `wordlists_dirb` are Docker named volumes defined in `docker-compose.yml`. Their contents persist across container restarts and upgrades. The `initializer` service also mounts both volumes to populate them on first run.
</Note>

Pre-installed wordlists have no checksum stored in the database, so their integrity is not verified on every use. Custom uploaded wordlists do store a checksum, which is re-verified each time the wordlist is selected as an input to confirm the file has not been modified since upload.

## Custom Wordlists

Any Admin or Auditor can upload their own wordlist files through the API or the UI. Uploaded wordlists are stored on the shared `rekono` volume so all worker containers can reach them.

**Wordlist fields returned by the API:**

| Field | Type | Description |
|-------|------|-------------|
| `id` | integer | Unique identifier of the wordlist. |
| `name` | string (max 100) | Human-readable label, unique across all wordlists. Used to identify the wordlist in the task creation form. |
| `type` | choice | `Endpoint` or `Subdomain` — determines which tools can use the wordlist. |
| `size` | integer | Number of lines (words) in the file, computed on upload. |
| `owner` | object | The user who uploaded the wordlist. `null` for default system wordlists. Only the owner (or an Admin) can update or delete the wordlist. |
| `liked` | boolean | Whether the current user has liked this wordlist. |
| `likes` | integer | Total number of users who have liked this wordlist. |

The `file` field is write-only and only accepted at creation time — the file content is stored on disk and cannot be replaced after upload.

<Tabs>
  <Tab title="Upload via API">
    Send a `multipart/form-data` POST request to `POST /api/wordlists/`:

    ```bash
    curl -X POST https://rekono.example.com/api/wordlists/ \
      -H "Authorization: Token <your-token>" \
      -F "name=my-endpoints" \
      -F "type=Endpoint" \
      -F "file=@/path/to/my-wordlist.txt"
    ```

    A successful response returns the new wordlist record, including the computed `size` (line count) and the `id` you will reference when creating tasks.
  </Tab>
  <Tab title="Update a wordlist">
    Only the wordlist `name` and `type` can be updated after creation — the file itself cannot be replaced. Send a `PUT` to `/api/wordlists/{id}/`:

    ```json
    {
      "name": "my-endpoints-v2",
      "type": "Endpoint"
    }
    ```

    Only the owner of the wordlist (or an Admin) can perform updates and deletions.
  </Tab>
  <Tab title="Delete a wordlist">
    ```bash
    DELETE /api/wordlists/{id}/
    ```

    Removes both the database record and the stored file. Only the wordlist owner or an Admin can delete a wordlist.
  </Tab>
</Tabs>

<Warning>
  Wordlists are shared across all projects, not scoped to individual ones. Every Admin and Auditor in the instance can see and use every registered wordlist, so apply naming conventions to make ownership and purpose clear.
</Warning>

## Assigning Wordlists to Tasks

When creating a task, you select one or more wordlists to supply to the tool executions via the `wordlists` many-to-many field on the `Task` model. The execution engine filters the selected wordlists at runtime — only those whose `type` matches the filter condition of a tool's argument input are passed to that specific tool.

For example, if you select both an `Endpoint` wordlist and a `Subdomain` wordlist when creating a task that runs Dirsearch, only the `Endpoint` wordlist will be passed to Dirsearch; the `Subdomain` wordlist is silently skipped because it does not match the argument filter.

```json
POST /api/tasks/
{
  "target": 1,
  "configuration": 5,
  "intensity": "Normal",
  "wordlists": [3, 7]
}
```

<Tip>
  "Like" wordlists you use frequently by clicking the star icon in the UI (or `POST /api/wordlists/{id}/like/`). Liked wordlists float to the top of the selection list, making it faster to configure new tasks.
</Tip>
